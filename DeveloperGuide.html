Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

PersonListPanel uses PersonCard for normal and filtered lists, and PersonDetailsCard for view INDEX. Both display the client's derived intention; prices and transaction statuses belong to the property's display. The detail card uses the client's name as its heading, labels each remaining field and shows the return-to-list hint. MainWindow creates one HelpWindow, which constructs a CommandHelpCard for each supported command. The current screens are illustrated in the User Guide.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a client).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Model component

API : Model.java

The Model component,

  • stores the client data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores each client's properties as an ordered, unmodifiable list within Person.
  • derives each client's ClientIntention from the immutable property list without storing a second role field.
  • applies a FilteredList<Person> and then a SortedList<Person> to the source client list. It exposes one unmodifiable displayed ObservableList<Person> to both the UI and index-based commands.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both client data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • uses JsonAdaptedPerson and JsonAdaptedProperty to preserve each client's property list and its order.
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Client input validation

Client add and edit call ParserUtil.rejectUnknownClientParameters() before tokenization so an unknown alphabetic field prefix such as x/ is reported as an unexpected parameter instead of being absorbed into a value. The existing manual-intention and removed-budget checks retain their dedicated messages. Phone accepts only 3 to 15 digits. Command parsing and saved-client loading share this validation; invalid saved phone numbers follow the normal data-loading error path without replacing the client file.

Protecting client data after a failed load

JsonUtil#fromJsonString() reads a complete value using Jackson's parser and checks that no token follows it. Trailing whitespace is accepted; additional values and malformed trailing text cause a loading error.

MainApp#initModelManager() propagates DataLoadingException when an existing client data file cannot be loaded. MainApp#init() then provides an error UI without creating a model or command logic. When the application starts, the error dialog shows the file's absolute path and recovery instructions, then the application exits. stop() skips saving preferences when no model was initialized.

This prevents command-triggered automatic saving from overwriting the failed file with an empty list. The user must repair or replace the file and restart. Moving the file aside explicitly selects the existing first-run behavior, which loads sample clients. A valid file containing an empty client list still loads normally.

Recovering invalid window preferences

JsonUserPrefsStorage#readUserPrefs() validates deserialized GUI settings before returning them. Null GUI settings and dimensions that are non-positive or non-finite cause DataLoadingException. MainApp#initPrefs() then uses its existing recovery path to load and save default preferences. Missing fields still use their defaults; valid negative screen coordinates and an unset position remain supported. Client data is independent of preferences and is not rewritten during this recovery.

Preventing concurrent instances

MainApp#init() acquires a DataFileLock before reading or saving preferences or client data. It holds a non-blocking, exclusive Java NIO file lock on a companion addressbook.json.lock file beside the resolved client data path. Equivalent paths share ownership, while independent data files can be used separately. An in-process owner map avoids reopening an already-owned companion file: closing a competing channel can release the original process's locks on some platforms.

If acquisition fails, startup supplies an error UI without creating storage, model or command logic. Contention explains that the other instance must be closed; other I/O failures report access instructions. MainApp#stop() releases the lock after saving preferences, including when saving fails. Unsuccessful initialization releases it in a finally block. JVM termination also releases the operating-system lock. The companion file remains in place to avoid races caused by deleting and recreating it; its existence alone does not indicate ownership. The lock coordinates RESIDEX instances, not external editors or older app versions.

DataFileLockTest uses separate headless Java processes to check contention, normal exit and forced termination. MainAppTest checks that rejected launches preserve client data and preferences, and failures release ownership.

Command reference help

HelpCommand returns a CommandResult with showHelp set to true. The existing MainWindow#handleHelp() method shows or focuses a single HelpWindow. The F1 shortcut uses the same method. HelpWindow#focus() clears the stage's iconified state before bringing it forward and requesting focus. Restoring an existing window keeps its size, position and scroll position; it does not construct a new reference.

HelpContent holds each command's description, syntax, notes and examples, using shared command words, prefixes and validation messages where appropriate. HelpWindow creates a CommandHelpCard for each entry. The cards sit inside a scrolling pane, with the heading and User Guide footer outside it. Each read-only example has a keyboard-accessible Copy button. CommandHelpCard copies its original example string using JavaFX's clipboard API; visual wrapping does not add line breaks. The button reports Copied or Failed and can be used again. Copy actions do not invoke command logic. The copy result updates the button's accessible text, retaining the example, and sends an accessibility text-change notification. A package-private constructor accepts a clipboard writer so tests can exercise failure and retry. The layout and styles are defined in HelpWindow.fxml, CommandHelpCard.fxml and HelpWindow.css. Help loads Residex.css first so text, buttons and focus indicators follow the main UI's light theme. HelpWindow.css scopes the reference layout and example-row sizing to the Help window.

The reference is bundled with the app and works offline. The footer's Copy URL button copies the RESIDEX User Guide URL. Update HelpContent and the User Guide together when commands change. HelpContentTest checks that the documented examples parse as the intended commands without executing them or starting JavaFX. ResidexUiTest checks deiconification, bounds and scroll-state preservation without a native window manager. Other automated checks cover exact example copying, accessible success/failure feedback and retry, the guide URL action, and off-screen wrapping at the default and minimum Help sizes. Clipboard contents are restored after tests that use the system clipboard.

Find command

FindCommandParser accepts exactly one of the shared CliSyntax prefixes: n/, e/, p/, l/, i/, s/, t/, pr/ or bd/. For example, find n/Alice Bob searches names; prefix letters are case-insensitive. Name, email, phone, and location searches use case-insensitive substring matching with OR semantics across keywords. LocationContainsKeywordsPredicate checks every entry in Person#getProperties() and returns a client once if any property location contains any keyword. Clients without properties do not match a location search. For example, find l/clementi matches clients with locations such as Clementi Ave 3 or Woodlands Clementi. Intention searches accept exactly one value, buyer, seller or both, case-insensitively. Missing keywords, repeated or mixed prefixes, and unsupported selectors are rejected. find i/unspecified is rejected. IntentionMatchesPredicate includes BOTH in buyer/seller searches and matches only BOTH for the both query. Its comparator ranks exact-role matches before mixed-role matches.

ModelManager maintains the following live list pipeline:

AddressBook source list -> FilteredList -> SortedList -> unmodifiable displayed list

For intention predicates, updateFilteredPersonList applies the role comparator and breaks ties using source-list positions. The tie-breaker preserves group order when a property command replaces a client and changes their role. An identity-based source-position lookup replaces repeated linear scans in the comparator. A source-list invalidation clears the lookup before changes reach the transformation lists; the next tie comparison rebuilds it in one pass. Later comparisons use constant-time lookups until the source changes again. This also releases old replacement instances and handles additions, deletions and complete address-book resets without stale positions. For every other predicate, including list, it clears the comparator, restoring source order. Neither filtering nor sorting reorders the AddressBook or saved client list.

getFilteredPersonList() returns this single displayed list to LogicManager and the UI. EditCommand, DeleteCommand, RemarkCommand and PropertyCommandUtil resolve client indexes from the same list. Property commands preserve the active filter, so a role-changing update can move or remove the client from results. IntentionSearchIntegrationTest verifies all six indexed operations against sorted results, first/last/invalid displayed indexes, live role changes, normal-order restoration and saved source order. ModelManagerIntentionOrderTest additionally checks replacements, source resets and 1,000 clients without timing assertions: intention sorting must not scan clients using Person#equals() to resolve ties.

Status searches accept one PropertyStatus token or the displayed phrase Not specified, ignoring case. FindCommandParser recognises the display alias after selector validation and otherwise shares PropertyParserUtil.parseStatus() with property commands while retaining the find command's validation order and error messages. PropertyStatusMatchesPredicate matches a client if any existing property has the requested status. The predicate returns false for an empty property list, including when searching for UNSPECIFIED. Multiple matching properties still produce one client result. The predicate bases both equality and hashing on the requested status.

Status results retain source order through the displayed list; a status query clears the intention comparator.

Type and price searches each accept exactly one value. find t/ reuses PropertyParserUtil.parseType(), so the same tokens as addp are accepted (HDB, Condominium, Landed, or h, c, l), ignoring case. PropertyTypeMatchesPredicate matches a client if any property has that type. find pr/ takes a range of whole-dollar amounts: MIN-MAX, MIN- or -MAX. FindCommandParser splits it on the single -, validates each bound with PropertyPrice.isValidPrice(), and rejects empty, malformed or reversed ranges with FindCommand#MESSAGE_INVALID_PRICE_RANGE. PropertyPriceInRangePredicate compares the inclusive bounds with each property's price. Properties without a price never match, and a client appears once even if several properties match. find bd/ accepts exactly one number and validates it with PropertyParserUtil.parseBedrooms(), so it shares the 1 to 20 range with addp and editp. PropertyBedroomsMatchesPredicate matches a client if any property has exactly that number of bedrooms; properties with unknown bedrooms never match. These predicates clear the intention comparator, so their results use normal client order. Replacing a property re-evaluates the active status predicate, so clients may leave the displayed results. PropertyStatusSearchIntegrationTest checks stages, selector coexistence, saved order and displayed-index targeting.

Derived client intention

Person#getIntention() computes a ClientIntention from the current property list on demand. Properties use PropertyIntention.BUYING and PropertyIntention.SELLING for their direction.

Buying-direction property present Selling-direction property present Derived role Display
No No UNSPECIFIED Not specified
Yes No BUYER Buyer
No Yes SELLER Seller
Yes Yes BOTH Buyer / Seller

No client intention field or constructor parameter is stored in Person. Equality and hashing use the properties, so they also reflect everything that determines the role. PersonBuilder and sample clients without properties produce UNSPECIFIED; no placeholder property is inferred. Fresh sample data gives Alex buying properties, Bernice selling properties and Charlotte both directions, while David, Irfan and Roy have no properties. This demonstrates every derived role and intention-search ordering without changing how real saved clients are loaded. All property-copy methods derive the new role automatically while leaving the original Person unchanged. copyWithProperties asserts that the replacement preserves client identity, an internal copy invariant. This assertion does not validate user input or perform required work. Gradle tests enable assertions by default.

AddCommandParser accepts name, phone and email; the client is initially UNSPECIFIED. Both client add and edit call ParserUtil.rejectClientIntention before tokenizing fields. This shared check raises ParseException for any standalone i/ field, including mixed case, blank and repeated values, preventing it from being absorbed into another field's text. Property commands still accept their own i/.

JsonAdaptedPerson accepts the legacy JSON intention parameter as ignored input and stores no role field. New JSON omits client intention; only properties determine the role after loading. A missing, null or stale legacy client role does not prevent otherwise valid data from loading. For example, legacy Buyer plus an empty property list becomes UNSPECIFIED; legacy Buyer plus only Selling properties becomes SELLER. Property-value validation and indexed storage errors remain unchanged. Round-trip tests cover all four roles, and legacy-file tests verify that loading does not rewrite the file.

Duplicate client feedback

AddCommand and EditCommand search the complete stored client list using Person#isSamePerson(Person) when checking for a conflict. This keeps the name-and-phone identity rule unchanged and finds conflicting clients outside the current filter. An edit that retains the selected client's identity is allowed without treating that client as its own duplicate. Both commands use the shared Messages.MESSAGE_DUPLICATE_PERSON format to identify the stored client's name and phone number and explain that name matching ignores capitalisation and extra spaces. The feedback does not use an index from the unfiltered list, since it could identify a different client in the displayed results. Conflicts throw CommandException before any model update or save occurs.

Client fields and property amounts

Clients store their name, phone, email, remark and ordered properties. Their role is derived from those properties. Monetary amounts belong only to property entries through PropertyPrice and pr/. add and edit call ParserUtil.rejectClientBudget before tokenization to reject the removed client b/ prefix in any position or case. This prevents a removed prefix from being accepted as part of another field's value.

JsonAdaptedPerson no longer stores or writes client budgets. The existing JSON reader ignores unknown fields, so older budget entries are discarded when loading and disappear on the next save. Other client fields, property order, prices and transaction statuses are preserved, as is the client's derived role. There is no client budget amount or colour band in either client list cards or the detail view.

Client property model

The property model, storage, numbered client-card display and addp, delp and editp commands are implemented. Client add omits intention, and client add/edit reject manual intention fields. Property fields belong to the separate property commands.

Fields and validation

Property is an immutable value object in seedu.address.model.property. Each entry describes one client's interest in buying or selling a property.

Field Type Rules
Type PropertyType Required: HDB, CONDOMINIUM, or LANDED. parse accepts full names and h, c, or l, ignoring case and surrounding whitespace.
Intention PropertyIntention Required: BUYING or SELLING. parse accepts Buying or Selling, ignoring case and surrounding whitespace. Client-role values are invalid. Property directions determine the derived ClientIntention.
Location PropertyLocation Required, nonblank text. Surrounding whitespace is removed; case and internal whitespace are preserved.
Price PropertyPrice Optional. A supplied price must be a positive whole-dollar SGD amount up to Long.MAX_VALUE, without commas, decimals, leading zeros, or surrounding whitespace.
Bedrooms PropertyBedrooms Optional. A whole number from 1 to 20 without leading zeros, a decimal point or a sign. getBedrooms() returns Optional.empty() when unknown.
Status PropertyStatus Always non-null internally. The six tokens ignore case and outer whitespace; omitted creation status defaults to UNSPECIFIED. Empty input is invalid.

Use the three-argument Property constructor when the price is unknown, or pass null as the fourth argument. getPrice() returns Optional.empty() for an unknown price. Zero is invalid for a property price. The three- and four-argument constructors default status to UNSPECIFIED. Use the five-argument constructor (type, intention, location, price, status) to record an explicit stage; price may be null, but status may not. getStatus() returns the enum directly. Amounts are stored only on property entries; there is no client budget field. For a buying property, price records the asking/current listing price; for a selling property, the client's asking price. Status edits do not change property prices automatically.

Transaction status

Each immutable Property owns one current status, independently of its direction and the client's other properties. Status participates in equality, hashing, display and diagnostic strings.

Enum / token Display Meaning
UNSPECIFIED / unspecified Not specified No transaction stage has been recorded for this property yet.
ENQUIRING / enquiring Enquiring The client has shown interest in buying or selling the property but has not committed to proceeding.
VIEWING / viewing Viewing For a Buying property, the agent arranges a client visit so the client can assess whether to proceed. For a Selling property, the agent visits and assesses the seller's property before representing and marketing it to prospective buyers. The agent is the intermediary; RESIDEX does not require the seller and prospective buyers to deal directly with each other.
NEGOTIATING / negotiating Negotiating The client intends to proceed and the relevant parties work toward agreement on price and other transaction terms.
CLOSING / closing Closing The main transaction terms are agreed, but contracts, signing, payment or other final formalities remain incomplete.
COMPLETED / completed Completed Required documents are signed, payment is completed and the property has been handed over.

This is a recorded assessment, not a one-way state machine. All old/new status pairs are permitted, including Viewing to Enquiring, Closing to Negotiating and corrections from Completed. Completed does not delete, archive or lock a property or client. Explicit delp/delete remains necessary. There is no client-level status, stage history, viewing-date field or automatic transition. The property-command token for Not specified is unspecified. Status search also accepts the display text Not specified, ignoring case and whitespace between its words; not-specified remains invalid. FindCommandParser handles this search alias after validating selectors, leaving property parsing and saved statuses unchanged.

PropertyIntention describes an individual property's buying or selling action. It is separate from ClientIntention, the role derived from all of the client's properties. Each Property has exactly one non-null intention, enforced by its constructor and the two-value enum. Changing a property's intention recomputes the client role and can change how find i/ matches or orders that client.

Ownership and indexes

Person owns a List<Property>, initially empty. The constructor copies incoming lists, rejects null lists and entries, and getProperties() exposes an unmodifiable list. Properties have no owner reference or permanent ID. Identical entries are allowed within a client and across clients; they are independent records.

Displayed property indexes start at 1 within each client. Appending adds to the end, replacing keeps the same position, and removing an entry shifts later entries down by one. For example, deleting property 2 from a three-entry list makes the former property 3 become property 2. The client-card display uses this same list order.

Property changes affect Person.equals() and hashCode(), including list order. They do not change the client's identity as determined by isSamePerson().

Commands and parsing

AddressBookParser normalises command words with Locale.ROOT, making command words case-insensitive. AddPropertyCommandParser, DeletePropertyCommandParser and EditPropertyCommandParser parse the three property commands. PropertyParserUtil recognises t/, i/, l/, pr/, bd/ and s/ case-insensitively without changing field values. Unknown and repeated fields are rejected, including repeated prefixes with different capitalisation. Whitespace-separated alphabetic words ending in / are reserved as prefixes and cannot be used as literal location text. Property type aliases and Buying/Selling values ignore case in property commands. PropertyParserUtil.parseIntention delegates to PropertyIntention.parse and translates invalid values into ParseException. Buyer, Seller, Both and blank values are rejected; legacy values are accepted only by storage.

addp CLIENT_INDEX t/TYPE i/INTENTION l/LOCATION [pr/PRICE] [bd/BEDROOMS] [s/STATUS] requires a type, intention and nonblank location. The parser validates every field before constructing a complete Property; an omitted price is unknown. An omitted status defaults to UNSPECIFIED, and omitted bedrooms are unknown. A supplied empty price, bedrooms or status is invalid when adding. delp CLIENT_INDEX PROPERTY_INDEX accepts exactly two positive indexes and no field arguments. editp CLIENT_INDEX PROPERTY_INDEX [t/TYPE] [i/INTENTION] [l/LOCATION] [pr/PRICE] [bd/BEDROOMS] [s/STATUS] requires at least one field. EditPropertyDescriptor copies the requested edits and distinguishes an omitted price or bedroom count from an explicitly cleared one. An empty pr/ clears the price and an empty bd/ clears the bedrooms on edit, while empty required fields are rejected. Omitted s/ preserves status; empty s/ is rejected. s/unspecified explicitly resets the stage. The descriptor copies a supplied non-null status and accepts status-only or combined edits. Invalid status tokens are translated from IllegalArgumentException to ParseException with the cause preserved.

PropertyCommandUtil resolves the client from model.getFilteredPersonList() and validates the property index within that client's list. Both indexes use the existing Index class and errors are reported through CommandException. Commands preserve the active client filter and all unrelated fields, including an omitted status. The derived role and displayed position can change. Changing or deleting a matching property can remove the client from status results; subsequent indexes use that new view. EditPropertyCommand constructs a replacement using the current values for omitted fields. Only after successful validation does it call model.setPerson once. An equal replacement reports no change and leaves the original Person in the model. Invalid parses or indexes leave both the model and saved data unchanged.

After a successful model.setPerson, EditPropertyCommand retains the generic FINE edit diagnostic and adds one FINE transition record only when the status actually changes. It uses the existing LogsCenter logger and a lazy message containing displayed client/property indexes and enum names:

Property status changed for displayed client 2, property 1: VIEWING -> NEGOTIATING

The diagnostic contains no client name, phone, email, location or full command/domain object. Same-status edits, changes to other fields, rejected indexes and failed model mutations produce no transition record. The existing default INFO level is unchanged. EditPropertyStatusLoggingTest temporarily attaches a FINE handler, checks that mutation precedes the record, and restores logger settings after each test. The handler verifies the underlying source client, including when a parsed status edit removes that client from find s/viewing results. The regression checks the original displayed indexes and a single PII-free record.

The add-property command applies the immutable model update after validating the displayed client index:

Property property = new Property(
        PropertyType.HDB, PropertyIntention.BUYING, new PropertyLocation("Clementi Ave 3"));
Person original = model.getFilteredPersonList().get(personIndex.getZeroBased());
Person updated = original.withAddedProperty(property);
model.setPerson(original, updated);

For editing, call original.withUpdatedProperty(propertyIndex, replacement) with a complete replacement property. The edit-property command preserves the original values for omitted fields. For deletion, call original.withoutProperty(propertyIndex). Both methods return a new person and throw IndexOutOfBoundsException when the property index is outside this client's list. All three methods preserve unrelated client fields and leave the original person unchanged. Apply the returned person through model.setPerson; calling a method alone does not update the model.

Existing EditCommand and RemarkCommand carry the property list into the replacement person so that changing contact details or remarks preserves all properties. Future code that reconstructs a Person must also preserve the list. The five-argument Person constructor creates a client with no properties; the six-argument constructor accepts the property list as its final argument.

Storage and compatibility

Each saved client has a properties array. JsonAdaptedProperty stores type, intention, and location as strings, price as a whole-dollar string or null when unknown, and status as a canonical enum name such as VIEWING. Property order and duplicate entries survive saving and loading. A missing price also loads as unknown. Missing or null legacy status loads as UNSPECIFIED; otherwise the status must be a recognised token. bedrooms is saved as a whole-number string, or null when unknown; a missing bedrooms field also loads as unknown, so older files still open. An invalid saved value is rejected like any other invalid property field. The adapter retains its four-argument convenience constructor for old callers and uses a five-field JSON creator. New saves always write a status for each property. Loading alone does not rewrite the file.

Property intentions are saved canonically as Buying or Selling. The adapter also accepts exact legacy Buyer and Seller values, mapping them to BUYING and SELLING. This compatibility rule stays in JsonAdaptedProperty and does not broaden command syntax. Legacy client-level intention is ignored and omitted from new saves; the client role is derived from properties. Mixed old/new property values can be loaded in one file. Reading does not rewrite the file; saving writes all property intentions in the new canonical form. Unlike CLI input, saved intention values are case-sensitive and do not permit surrounding whitespace.

JsonAdaptedPerson treats a missing or null properties field as an empty list, so valid v1.3 files load without migration. Null property entries, missing required fields, and invalid values are rejected with IllegalValueException; the error includes the property's one-based index. File loading reports these errors as DataLoadingException. Invalid entries are not silently discarded. An invalid or blank persisted status follows the same indexed IllegalValueException/DataLoadingException path; it is not replaced with a default. File-level tests check that rejected loads leave the original bytes untouched.

The regression tests cover field validation, case-insensitive parsing, price clearing, index changes, independent clients and preservation through client edits and remarks. Integration tests execute command strings through the real parser, model and JSON storage, checking unchanged data after rejected operations and persistence after valid operations. Old-file compatibility and property-list immutability are also covered. Storage tests assert canonical output, legacy read-save-read migration, mixed representations, and preserved order, duplicates and client fields. Invalid property intentions retain the indexed IllegalValueException error path; full-file reads fail without changing the input file. Status coverage includes all six parse/display values, locale independence, all 36 old/new stage pairs, omission/default/reset behavior, canonical round trips, invalid legacy data, Completed edits, live status-filter membership and exact transition-log content/suppression.

Property display

PersonCard renders one wrapped label per property, using its one-based list position and Property#toDisplay(). The property list is hidden when empty, and PersonListPanel measures each card at its available width so longer locations expand the row. Type, property intention, location, a known price and readable status are displayed together; an unknown price has no amount, while UNSPECIFIED displays as Not specified. HelpContent includes the three property commands and its examples are parsed by HelpContentTest.

Viewing complete client details

ViewCommandParser delegates index validation to ParserUtil.parseIndex. ViewCommand resolves that index against Model#getFilteredPersonList() before changing the filter, so search-result indexes are respected. An out-of-range index raises CommandException without changing the filter. A valid request filters by the selected client's identity through Model#showPersonDetails. No client records are changed. ModelManager owns an observable ClientViewMode: ALL_CLIENTS, FILTERED_CLIENTS or CLIENT_DETAILS. list uses the existing show-all predicate to restore all clients in stored order and clear search mode.

Logic exposes the model's read-only display mode, which MainWindow passes to PersonListPanel. The heading follows this mode, so a search matching all or no clients still shows Filtered clients. Each cell observes detail mode with a weak listener and immediately replaces its graphic with PersonDetailsCard or the usual PersonCard, including when JavaFX reuses cells after list. This avoids leaving detail cards visible until a later layout pulse. The panel displays the return hint above the scrollable list. The detail card uses the client's name as its heading and lays out the other four scalar client fields and every property's six fields in labelled, wrapping rows. The Bedrooms row shows the recorded count, or Not recorded when absent. Missing optional values use explicit placeholders. Undo/redo feature

Implementation

The undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as a states list and a currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current client data state in its history.
  • VersionedAddressBook#undo() -- Restores the previous client data state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone client data state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Each data-changing command (add, edit, delete, remark, addp, editp and delp) calls Model#commitAddressBook() after it succeeds. A command that fails, or an editp that leaves the property unchanged, does not commit. edit and remark also skip the commit when the edited client equals the original, so an edit that changes nothing does not clear what can be redone. The history keeps the VersionedAddressBook#MAX_UNDOABLE_CHANGES (100) most recent changes, which is 101 saved states including the current one, dropping the oldest first. The undo and redo commands also reset the displayed list to show all clients.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial client data state, and the currentStatePointer pointing to that single client data state.

Step 2. The user executes delete 5 command to delete the 5th client in RESIDEX. The delete command calls Model#commitAddressBook(), causing the modified state of the client data after the delete 5 command executes to be saved in the states, and the currentStatePointer is shifted to the newly inserted client data state.

Step 3. The user executes add n/David …​ to add a new client. The add command also calls Model#commitAddressBook(), causing another modified client data state to be saved into the states.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the client data state will not be saved into the states.

Step 4. The user now decides that adding the client was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous client data state, and restores the client data to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial client data state, then there are no previous client data states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Glossary

  • Active property listing: A property listing recorded under a seller's client profile that is currently available for sale.
  • Associated property: A property linked to a client's profile, such as a property the client is interested in or is selling.
  • Buyer: A client who wants to purchase a property.
  • Buying: A property intention describing a client's interest in purchasing that property.
  • Buying status: How close a client is to agreeing on a property.
  • Client: A person whose details a property agent stores in RESIDEX; their property-derived role can be Buyer, Seller, both or Not specified.
  • Client intention: The role derived from the client's property directions; no properties means Not specified, and both directions means Buyer / Seller.
  • Client detail view: The single-client display opened by view INDEX, showing every stored client and property field, including placeholders for missing optional values. The displayed client has index 1; list returns to all clients.
  • Client index: A client's one-based position in the currently displayed list, including search results or the detail view. It is not a permanent identifier.
  • Client information history (planned, not yet implemented): Previously recorded information or changes associated with a client, available for review.
  • Client profile: The stored information about a client, including contact details, remark and associated properties with their individual transaction stages.
  • Duplicate client: A client whose normalised name and normalised phone number both match those of an existing client.
  • Filtered client list: The clients displayed after find or view. Each find searches all stored clients; view selects one displayed client. list restores all clients in stored order.
  • Follow-up (planned, not yet implemented): A planned next contact with a client. A follow-up may be upcoming or overdue.
  • Intention: Whether a client or property is on the buying or selling side.
  • Internal note (planned, not yet implemented): A note attached to a client profile that is not displayed in the client list. It does not imply additional access control or encryption.
  • Keyword: A search term supplied after a find prefix. Whitespace separates keywords, and any matching keyword returns a client.
  • Lead: A potential client or transaction that the property agent is currently pursuing
  • Mainstream OS: Windows, Linux, Unix, or macOS.
  • Minimum Viable Product (MVP): The initial version of RESIDEX containing the features selected to meet its core user needs.
  • Prefix: A field selector such as n/ for a name or l/ for a property location. The find command accepts exactly one selector.
  • Priority (planned, not yet implemented): An indication of a client's importance or urgency, assigned by the property agent to help decide whom to attend to first.
  • Private client note (planned, not yet implemented): A note attached to a client's profile whose contents are hidden from the client list.
  • Private contact detail: A contact detail that is not meant to be shared with others
  • Property agent: A user who manages buyers and sellers, and who prefers typing commands to using the mouse.
  • Property bedrooms: An optional whole number from 1 to 20 recording how many bedrooms a property has.
  • Property entry: A record in a client's ordered property list that stores information about an associated property.
  • Property index: The one-based position of a property entry within a selected client's property list. It is not a permanent identifier: deleting an earlier property shifts subsequent indexes down by one.
  • Property intention: The Buying or Selling action recorded for one property; these actions determine the client's derived role.
  • Property listing: A record containing information about a property available for sale or rent
  • Property location: Nonblank descriptive text stored on a property entry, such as Clementi Ave 3. The find l/ search checks these locations.
  • Property price: An optional, positive whole-dollar amount recorded for a property.
  • Property type: The HDB, Condominium or Landed category of a property entry.
  • Property status: A property's current recorded transaction stage: Not specified, Enquiring, Viewing, Negotiating, Closing or Completed. It can be corrected in either direction and is not a client-level field.
  • Property viewing (planned, not yet implemented): An appointment for a client to inspect a property
  • Purpose: A client's buying or selling needs, represented by property intentions and summarised by the derived client role.
  • Redo: Re-applying a change that undo reversed.
  • Remark: Text recorded for a client using the remark command and displayed on the client card.
  • Requirement: A condition a client wants in a property, such as preferred location, property type, or number of bedrooms.
  • Seller: A client who wants to sell a property.
  • Selling: A property intention describing a client's interest in selling that property.
  • Substring matching: Matching text that contains a keyword anywhere, ignoring case; for example, clementi matches both Clementi Ave 3 and Woodlands Clementi.
  • Transaction: The process of completing a property sale or rental
  • Undo: Reversing the most recent data-changing command. Up to 100 changes can be undone while RESIDEX is running.
  • Viewing: A property stage covering a buying client's assessment visit or the agent's visit to assess a seller's property before representation and marketing. It does not record an appointment date.
