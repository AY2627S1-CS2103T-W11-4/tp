Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

The Model component,

  • stores the client data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores each client's properties as an ordered, unmodifiable list within Person.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both client data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • uses JsonAdaptedPerson and JsonAdaptedProperty to preserve each client's property list and its order.
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Command reference help

HelpCommand returns a CommandResult with showHelp set to true. The existing MainWindow#handleHelp() method shows or focuses a single HelpWindow. The F1 shortcut and Help menu use the same method.

HelpContent holds each command's description, syntax, notes and examples, using shared command words, prefixes and validation messages where appropriate. HelpWindow creates a CommandHelpCard for each entry. The cards are display-only and sit inside a scrolling pane, with the heading and User Guide footer outside it. The layout and styles are defined in HelpWindow.fxml, CommandHelpCard.fxml and HelpWindow.css.

The reference is bundled with the app and works offline. The footer's Copy URL button copies the RESIDEX User Guide URL. Update HelpContent and the User Guide together when commands change. HelpContentTest checks that the documented examples parse as the intended commands without executing them or starting JavaFX.

Find command

FindCommandParser accepts exactly one of the shared CliSyntax prefixes: n/, e/, p/, or i/. For example, find n/Alice Bob searches names; prefix letters are case-insensitive. Name, email, and phone searches use substring matching with OR semantics across keywords. Intention searches accept exactly one value, buyer or seller, case-insensitively. Missing keywords, repeated or mixed prefixes, and unsupported selectors are rejected. FindCommand replaces the filter on the complete client list without modifying stored clients.

Duplicate client feedback

AddCommand and EditCommand search the complete stored client list using Person#isSamePerson(Person) when checking for a conflict. This keeps the name-and-phone identity rule unchanged and finds conflicting clients outside the current filter. An edit that retains the selected client's identity is allowed without treating that client as its own duplicate. Both commands use the shared Messages.MESSAGE_DUPLICATE_PERSON format to identify the stored client's name and phone number and explain that name matching ignores capitalisation and extra spaces. The feedback does not use an index from the unfiltered list, since it could identify a different client in the displayed results. Conflicts throw CommandException before any model update or save occurs.

Budget feature

Implementation

A client's budget is optional. Budget stores a non-negative whole-dollar amount. BudgetBand classifies that amount.

The bands are:

  • Low: $800,000 and below.
  • Middle: above $800,000, up to and including $2,500,000.
  • High: above $2,500,000.

add and edit accept the amount with the b/ prefix. Omitting b/ on add stores no budget. Omitting b/ on edit keeps the client's current budget. An invalid amount, such as a decimal, a comma, or a leading zero, is rejected and the stored client is left unchanged.

JsonAdaptedPerson writes the amount as a whole-dollar string. A saved client with no budget field loads with no budget. PersonCard shows the amount on the right of the card. Low is red, Middle is yellow, and High is green. A client with no budget has no amount on the card.

RemarkCommand copies the existing budget onto the updated client, so adding a remark does not remove it.

Design considerations

Aspect: Whether every client must have a budget

  • Alternative 1 (current choice): The budget is optional.
    • Pros: Sellers and existing saved files can omit it. Old data files still load.
    • Cons: The card does not show an amount for every client.
  • Alternative 2: Require a budget in every add command.
    • Pros: Every card shows a coloured amount.
    • Cons: Existing data files without a budget cannot be loaded, and a seller must be given an amount that may not mean anything.

Aspect: How the amount is stored

  • Alternative 1 (current choice): Store the whole-dollar amount and derive the colour from BudgetBand.
    • Pros: The user can enter any valid amount. The colour stays consistent with the thresholds.
    • Cons: The colour is not stored, so changing a threshold changes the colour of existing clients.
  • Alternative 2: Store the colour the user picks.
    • Pros: The displayed colour stays as the user left it.
    • Cons: The colour can disagree with the amount.

Client property model

The property model, storage, numbered client-card display and addp, delp and editp commands are implemented. Existing client add and edit commands retain their syntax; property fields belong to the separate property commands.

Fields and validation

Property is an immutable value object in seedu.address.model.property. Each entry describes one client's interest in buying or selling a property.

Field Type Rules
Type PropertyType Required: HDB, CONDOMINIUM, or LANDED. parse accepts full names and h, c, or l, ignoring case and surrounding whitespace.
Intention Intention Required: BUYER or SELLER. This belongs to the property and is independent of the client's existing intention. Intention.parse accepts exactly Buyer or Seller.
Location PropertyLocation Required, nonblank text. Surrounding whitespace is removed; case and internal whitespace are preserved.
Price PropertyPrice Optional. A supplied price must be a positive whole-dollar SGD amount up to Long.MAX_VALUE, without commas, decimals, leading zeros, or surrounding whitespace.

Use the three-argument Property constructor when the price is unknown, or pass null as the fourth argument. getPrice() returns Optional.empty() for an unknown price. Zero is invalid for a property price. The existing client budget remains a separate field with its existing validation.

Ownership and indexes

Person owns a List<Property>, initially empty. The constructor copies incoming lists, rejects null lists and entries, and getProperties() exposes an unmodifiable list. Properties have no owner reference or permanent ID. Identical entries are allowed within a client and across clients; they are independent records.

Displayed property indexes start at 1 within each client. Appending adds to the end, replacing keeps the same position, and removing an entry shifts later entries down by one. For example, deleting property 2 from a three-entry list makes the former property 3 become property 2. The client-card display uses this same list order.

Property changes affect Person.equals() and hashCode(), including list order. They do not change the client's identity as determined by isSamePerson().

Commands and parsing

AddressBookParser normalises command words with Locale.ROOT, making command words case-insensitive. AddPropertyCommandParser, DeletePropertyCommandParser and EditPropertyCommandParser parse the three property commands. PropertyParserUtil recognises t/, i/, l/ and pr/ case-insensitively without changing field values. Unknown and repeated fields are rejected, including repeated prefixes with different capitalisation. Whitespace-separated alphabetic words ending in / are reserved as prefixes and cannot be used as literal location text. Property type aliases and Buyer/Seller values ignore case in property commands; the underlying property intention enum remains unchanged.

addp CLIENT_INDEX t/TYPE i/INTENTION l/LOCATION [pr/PRICE] requires a type, intention and nonblank location. The parser validates every field before constructing a complete Property; an omitted price is unknown. A supplied empty price is invalid when adding. delp CLIENT_INDEX PROPERTY_INDEX accepts exactly two positive indexes and no field arguments. editp CLIENT_INDEX PROPERTY_INDEX [t/TYPE] [i/INTENTION] [l/LOCATION] [pr/PRICE] requires at least one field. EditPropertyDescriptor copies the requested edits and distinguishes an omitted price from an explicitly cleared price. An empty pr/ clears the price on edit, while empty required fields are rejected.

PropertyCommandUtil resolves the client from model.getFilteredPersonList() and validates the property index within that client's list. Both indexes use the existing Index class and errors are reported through CommandException. Commands preserve the active client filter and all unrelated fields. EditPropertyCommand constructs a replacement using the current values for omitted fields. Only after successful validation does it call model.setPerson once. An equal replacement reports no change and leaves the original Person in the model. Invalid parses or indexes leave both the model and saved data unchanged.

The add-property command applies the immutable model update after validating the displayed client index:

Property property = new Property(
        PropertyType.HDB, Intention.BUYER, new PropertyLocation("Clementi Ave 3"));
Person original = model.getFilteredPersonList().get(personIndex.getZeroBased());
Person updated = original.withAddedProperty(property);
model.setPerson(original, updated);

For editing, call original.withUpdatedProperty(propertyIndex, replacement) with a complete replacement property. The edit-property command preserves the original values for omitted fields. For deletion, call original.withoutProperty(propertyIndex). Both methods return a new person and throw IndexOutOfBoundsException when the property index is outside this client's list. All three methods preserve unrelated client fields and leave the original person unchanged. Apply the returned person through model.setPerson; calling a method alone does not update the model.

Existing EditCommand and RemarkCommand carry the property list into the replacement person so that changing contact details or remarks preserves all properties. Future code that reconstructs a Person must also preserve the list. The original six-argument Person constructor creates a client with no properties; the seven-argument constructor accepts the property list as its final argument.

Storage and compatibility

Each saved client has a properties array. JsonAdaptedProperty stores type, intention, and location as strings, and price as a whole-dollar string or null when unknown. Property order and duplicate entries survive saving and loading. A missing price also loads as unknown.

JsonAdaptedPerson treats a missing or null properties field as an empty list, so valid v1.3 files load without migration. Null property entries, missing required fields, and invalid values are rejected with IllegalValueException; the error includes the property's one-based index. File loading reports these errors as DataLoadingException. Invalid entries are not silently discarded.

The regression tests cover field validation, case-insensitive parsing, price clearing, index changes, independent clients and preservation through client edits and remarks. Integration tests execute command strings through the real parser, model and JSON storage, checking unchanged data after rejected operations and persistence after valid operations. Old-file compatibility and property-list immutability are also covered.

Property display

PersonCard renders one wrapped label per property, using its one-based list position and Property#toDisplay(). The property list is hidden when empty, and PersonListPanel measures each card at its available width so longer locations expand the row. Type, property intention, location and a known price are displayed together; an unknown price has no amount. HelpContent includes the three property commands and its examples are parsed by HelpContentTest.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current client data state in its history.
  • VersionedAddressBook#undo() -- Restores the previous client data state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone client data state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial client data state, and the currentStatePointer pointing to that single client data state.

Step 2. The user executes delete 5 command to delete the 5th person in RESIDEX. The delete command calls Model#commitAddressBook(), causing the modified state of the client data after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted client data state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified client data state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the client data state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous client data state, and restores the client data to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial client data state, then there are no previous client data states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

The redo command does the opposite — it calls Model#redoAddressBook(), which shifts the currentStatePointer once to the right, pointing to the previously undone state, and restores the client data to that state.

Note: If the currentStatePointer is at index addressBookStateList.size() - 1, pointing to the latest client data state, then there are no undone client data states to restore. The redo command uses Model#canRedoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the redo.

Step 5. The user then decides to execute the command list. Commands that do not modify the client data, such as list, will usually not call Model#commitAddressBook(), Model#undoAddressBook() or Model#redoAddressBook(). Thus, the addressBookStateList remains unchanged.

Step 6. The user executes delete 1, which calls Model#commitAddressBook(). Since the currentStatePointer is not pointing at the end of the addressBookStateList, all client data states after the currentStatePointer will be purged. Reason: It no longer makes sense to redo the add n/David … command. This is the behavior that most modern desktop applications follow.

  • Alternative 2: Individual command knows how to undo/redo by itself.

Appendix: Requirements

Product scope

Target user profile:

  • is a property agent who manages multiple clients and property listings
  • needs to record, search, and update client preferences and property details efficiently
  • tracks property viewings, follow-ups, leads, and ongoing transactions
  • prefers fast CLI-based interactions for managing information
  • needs to filter clients by categories such as buyer, seller, tenant, or landlord

Value proposition: RESIDEX provides property agents with a fast and organised way to manage buyers, sellers, property listings, viewings, and follow-ups in one place. Its efficient CLI-based commands allow agents to quickly retrieve, update, and filter information, reducing administrative work and helping them organise clients by category.

Use cases

For all use cases below, the System is RESIDEX and the Actor is a property agent. MSS stands for Main Success Scenario. These use cases describe product requirements, including features planned for future iterations; they do not indicate that a feature is already implemented.

A client is a buyer or seller. Two clients are duplicates when both their normalised names and normalised phone numbers match, following the Add Client feature specification. Names are compared case-insensitively after trimming surrounding spaces and replacing consecutive spaces with one space. Phone input is trimmed during parsing; valid phone numbers contain only digits and are compared exactly, including leading zeros. Email, intention, budget and remark do not affect duplicate detection. Person#isSamePerson(Person) applies this rule to additions, edits and loading saved data. Person#equals(Object) still compares all stored fields exactly. A client selected for an operation must belong to the currently displayed list. For deletion, the client is identified by their index in that list, including when it contains search results.

Precondition for all use cases: RESIDEX is running.

Guarantees: Read-only use cases leave stored client information unchanged. For requests to add, update or delete information, invalid input is rejected without changing that information.

Non-Functional Requirements

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. Should be able to hold up to 1000 persons without noticeable sluggishness in performance for typical usage.
  3. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.

Glossary

  • Active property listing: A property listing recorded under a seller's client profile that is currently available for sale.
  • Associated property: A property linked to a client's profile, such as a property the client is interested in or is selling.
  • Budget: The amount of money a buyer is prepared to spend on a property.
  • Buyer: A client who wants to purchase a property.
  • Buying status: How close a client is to agreeing on a property.
  • Client: A buyer or seller whose details a property agent stores in RESIDEX.
  • Client information history: Previously recorded information or changes associated with a client, available for review.
  • Client profile: The stored information about a client, including contact details, requirements, buying status, priority and associated properties.
  • Duplicate client: A client whose normalised name and normalised phone number both match those of an existing client.
  • Follow-up: A planned next contact with a client. A follow-up may be upcoming or overdue.
  • Internal note: A note attached to a client profile that is not displayed in the client list. It does not imply additional access control or encryption.
  • Lead: A potential client or transaction that the property agent is currently pursuing
  • Mainstream OS: Windows, Linux, Unix, or macOS.
  • Minimum Viable Product (MVP): The initial version of RESIDEX containing the features selected to meet its core user needs.
  • Priority: An indication of a client's importance or urgency, assigned by the property agent to help decide whom to attend to first.
  • Private client note: A note attached to a client's profile whose contents are hidden from the client list.
  • Private contact detail: A contact detail that is not meant to be shared with others
  • Property agent: A user who manages buyers and sellers, and who prefers typing commands to using the mouse.
  • Property listing: A record containing information about a property available for sale or rent
  • Property viewing: An appointment for a client to inspect a property
  • Purpose: A client's reason for engaging the property agent, recorded as Buyer or Seller.
  • Requirement: A condition a client wants in a property, such as budget, preferred location, property type, or number of bedrooms.
  • Seller: A client who wants to sell a property.
  • Transaction: The process of completing a property sale or rental
  • Viewing: A scheduled visit to a property with a client.
